# Model Context Protocol (MCP) — Masterclass & Overview

The **Model Context Protocol (MCP)** is an open specification originally introduced by Anthropic (and expanded by Hugging Face and the open-source AI community) that standardizes how AI models (LLMs and Autonomous Agents) connect with external tools, databases, APIs, local development environments, and data sources.

MCP is universally described as **"The USB-C for AI Applications."** Just as USB-C replaced dozens of proprietary, custom charging and peripheral cables with a single standardized physical and logical interface, MCP provides a universal protocol linking any AI application to any data source or tool.

---

## 1. What is Model Context Protocol?

### The Core Problem
Large Language Models (LLMs) are extraordinarily capable at reasoning, writing code, and analyzing patterns. However, they are inherently isolated:
- They are constrained by static training cutoffs.
- They lack direct access to real-time information (e.g., live databases, current news, web APIs).
- They cannot natively interact with local filesystems, execute shell commands, or trigger external workflows without custom integrations.

### The Solution
MCP bridges this gap by providing an open **JSON-RPC 2.0** messaging standard between AI applications and external software services. 

With MCP:
- **AI Hosts & Clients** (such as Claude Desktop, Cursor IDE, LangChain, or smolagents) implement the client side **once**.
- **Tool & Data Providers** (such as PostgreSQL, GitHub, Notion, text-processing tools, or local filesystems) implement an MCP server **once**.
- Any MCP Client can instantly discover and execute capabilities on any MCP Server with zero additional glue code.

## 2. The Integration Challenge: $M \times N$ vs. $M + N$

To understand why MCP is essential for modern AI architecture, consider the **$M \times N$ Integration Problem**.

### Without MCP: $M \times N$ Custom Glue Code
Without a standard protocol, connecting $M$ AI applications to $N$ external tools requires writing and maintaining **$M \times N$** custom integrations.

Each integration requires bespoke authentication, unique schema mapping, custom error handling, and manual prompt maintenance. Adding 1 new tool forces developers to update all $M$ applications; creating 1 new AI application requires re-implementing $N$ integrations from scratch.

## 3. Key Concepts & Core Terminology

Using clear, standardized terminology is crucial when building MCP applications.

> [!WARNING]
> **Host vs. Client**: Many articles use *Host* and *Client* interchangeably, but technically:
> - **Host**: The overall user-facing application (e.g. Claude Desktop, Cursor IDE, custom python script).
> - **Client**: The internal component within the Host that manages a 1:1 connection with a specific MCP Server.

<ClientServerRolesDiagram />

### The 3 Architectural Entities

1. **Host**: The user-facing AI application end-users interact with directly. Hosts manage user permissions, UI rendering, and overall LLM orchestration.
2. **Client**: A component running inside the Host application that maintains a dedicated 1:1 connection with a specific MCP Server, handling JSON-RPC protocol messages.
3. **Server**: An external process or remote web service exposing capabilities (Tools, Resources, Prompts) via the MCP standard format.

## 4. MCP Capabilities: Tools, Resources, Prompts & Sampling

An MCP Server can expose four distinct capabilities. An application's total value is the sum of the capabilities it provides.

<McpCapabilityTypesDiagram />

### Capabilities Breakdown

| Capability | Control & Trigger | Description | Real-World Example |
| :--- | :--- | :--- | :--- |
| **Tools** | Invoked by LLM (with user consent) | Executable functions that perform computational actions or retrieve dynamic data. | `execute_python_code`, `query_postgres_db`, `post_slack_message`. |
| **Resources** | Read-only pulled by Host | Passive data feeds (files, schemas, logs) exposed via URI schemes (`file://`, `postgres://`). | `file:///project/src/main.py`, `postgres://analytics/users_table`. |
| **Prompts** | Triggered by User / Host | Pre-defined templates or workflows guiding model-user interactions. | `code_review_style`, `generate_postmortem_template`. |
| **Sampling** | Server $\rightarrow$ Host request | Server-initiated requests asking the Host's LLM to generate completions for recursive evaluation. | Server asks Host LLM to review generated code before returning result. |

## 5. Architectural Components & Communication Flow

MCP operates on a structured request-response and notification pattern encoded over JSON-RPC 2.0.

### Interactive 7-Step Protocol Inspector
Step through the 7 stages of an MCP tool call request and inspect live wire JSON-RPC frames:

<McpProtocolMessageInspector />

### The 7-Step Communication Sequence

<CommunicationPatternSequenceDiagram />

<McpLifecycleSequenceDiagram />

1. **User Interaction**: User asks a query or submits a task to the **Host** application.
2. **Host & LLM Processing**: The Host passes context to the LLM. The LLM determines an external tool call is required.
3. **Client Connection**: The Host's **MCP Client** establishes a channel to the appropriate **MCP Server**.
4. **Initialization Handshake**: Client sends an `initialize` JSON-RPC request containing client version and capabilities; Server responds with protocol negotiation.
5. **Capability Discovery**: Client requests `tools/list` or `resources/list` to retrieve exact JSON Schema specifications.
6. **Tool Execution**: Client sends `tools/call` with argument payload. The Server executes the underlying function safely.
7. **Result Delivery**: Server returns result in a standard `content` array format `{"content": [{"type": "text", "text": "..."}]}`.

## 6. Transports: Local (`stdio`) vs Remote (`Streamable HTTP / SSE`)

MCP decouples protocol semantics from byte transport mechanics:

<McpLocalVsRemoteDiagram />

<TransportComparisonDiagram />

- **`stdio` (Local Subprocess)**: The Host launches the MCP Server as a local subprocess. Requests pass over `stdin`, responses over `stdout`, and logging over `stderr`. Ideal for local IDEs and local dev tools.
- **Streamable HTTP / SSE (Remote Service)**: The Server exposes a web endpoint (e.g., `http://localhost:7860/gradio_api/mcp/sse` or `https://api.example.com/mcp`). Client issues POST requests and listens over Server-Sent Events (SSE). Ideal for cloud services and microservices.

### Option A: Python FastMCP Server

```bash
pip install mcp
```

Create `server.py`:
```python
from mcp.server.fastmcp import FastMCP

# 1. Initialize FastMCP Server
mcp = FastMCP("Analytics Server")

# 2. Define an Executable Tool
@mcp.tool()
def analyze_sentiment(text: str) -> dict:
    """Analyzes text sentiment polarity and returns structured assessment."""
    text_lower = text.lower()
    score = 0.8 if "great" in text_lower or "love" in text_lower else -0.8 if "bad" in text_lower else 0.0
    
    return {
        "text": text,
        "score": score,
        "assessment": "positive" if score > 0 else "negative" if score < 0 else "neutral"
    }

# 3. Define a Read-Only Resource
@mcp.resource("config://app-settings")
def get_config() -> str:
    """Exposes system configuration string."""
    return "ENVIRONMENT=production\nLOG_LEVEL=info"

# 4. Define a Prompt Template
@mcp.prompt()
def summarize_report(topic: str) -> str:
    """Generates a prompt template for executive summarization."""
    return f"Please provide a 3-bullet executive summary of the latest reports regarding '{topic}'."

if __name__ == "__main__":
    mcp.run(transport="stdio")
```

### Option B: Gradio MCP Server (Web UI + MCP Endpoint + HF Spaces)

Gradio allows turning any Python function into both a Web UI and an MCP Server automatically with `mcp_server=True`.

```bash
pip install "gradio[mcp]" textblob
```

Create `app.py`:
```python
import json
import gradio as gr
from textblob import TextBlob

def sentiment_analysis(text: str) -> str:
    """
    Analyzes sentiment of text.
    
    Args:
        text (str): Input text string
    Returns:
        str: JSON formatted string containing polarity and assessment
    """
    blob = TextBlob(text)
    sentiment = blob.sentiment
    
    result = {
        "polarity": round(sentiment.polarity, 2),
        "subjectivity": round(sentiment.subjectivity, 2),
        "assessment": "positive" if sentiment.polarity > 0 else "negative" if sentiment.polarity < 0 else "neutral"
    }
    return json.dumps(result)

demo = gr.Interface(
    fn=sentiment_analysis,
    inputs=gr.Textbox(placeholder="Enter text..."),
    outputs=gr.Textbox(),
    title="Text Sentiment Analysis MCP Server"
)

if __name__ == "__main__":
    # Enables both Web UI at http://localhost:7860 and MCP SSE at /gradio_api/mcp/sse
    demo.launch(mcp_server=True)
```

### Option C: TypeScript MCP Server

```bash
npm install @modelcontextprotocol/sdk
```

```typescript
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { CallToolRequestSchema, ListToolsRequestSchema } from "@modelcontextprotocol/sdk/types.js";

const server = new Server(
  { name: "ts-calculator", version: "1.0.0" },
  { capabilities: { tools: {} } }
);

server.setRequestHandler(ListToolsRequestSchema, async () => ({
  tools: [
    {
      name: "add",
      description: "Adds two numbers",
      inputSchema: {
        type: "object",
        properties: { a: { type: "number" }, b: { type: "number" } },
        required: ["a", "b"]
      }
    }
  ]
}));

server.setRequestHandler(CallToolRequestSchema, async (request) => {
  if (request.params.name === "add") {
    const { a, b } = request.params.arguments as { a: number; b: number };
    return { content: [{ type: "text", text: String(a + b) }] };
  }
  throw new Error("Tool not found");
});

await server.connect(new StdioServerTransport());
```

## 8. Step-by-Step Guide: How to Build an MCP Client

An MCP Client connects to a server process, initializes protocol negotiation, retrieves available tool definitions, and executes tool calls.

### Python Client Session (`mcp.ClientSession`)

```python
import asyncio
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def main():
    # 1. Define server command & args
    server_params = StdioServerParameters(
        command="python",
        args=["server.py"]
    )

    # 2. Open stdio channel
    async with stdio_client(server_params) as (read, write):
        # 3. Create client session
        async with ClientSession(read, write) as session:
            # 4. Handshake initialization
            await session.initialize()
            print("✓ MCP Session initialized!")

            # 5. List available tools
            tools = await session.list_tools()
            print("Server Tools:", [t.name for t in tools.tools])

            # 6. Execute tool call
            result = await session.call_tool(
                "analyze_sentiment",
                arguments={"text": "Neural Mastery is an amazing platform!"}
            )
            
            for content in result.content:
                if content.type == "text":
                    print("Tool Result:", content.text)

if __name__ == "__main__":
    asyncio.run(main())
```

### Remote Server Proxy (`mcp-remote`)
If an MCP Client app only supports local `stdio` subprocesses, you can bridge it to a remote SSE server (such as a Hugging Face Space) using `mcp-remote`:

```json
{
  "mcpServers": {
    "hf-sentiment": {
      "command": "npx",
      "args": [
        "mcp-remote",
        "https://YOUR_USERNAME-mcp-sentiment.hf.space/gradio_api/mcp/sse"
      ]
    }
  }
}
```
