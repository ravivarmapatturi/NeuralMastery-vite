# Hyperparameter Optimization

[Model Evaluation & Metrics](/docs/machine-learning/model-evaluation-metrics) covers *what* to measure. This page covers the actual search problem underneath "tune the hyperparameters": model hyperparameters (learning rate, tree depth, regularization strength, number of layers) aren't learned from data the way weights are — they have to be searched over, using validation performance (see [ML Workflow Fundamentals](/docs/machine-learning/ml-workflow-fundamentals#train-validation-test-splits)) as the search signal, never the test set.

<ELI5>

Imagine tuning an old radio with two knobs — one actually changes the station, the other does nothing (it's broken). If you test every combination of both knobs systematically (a grid), you waste half your turns twiddling the broken knob while barely varying the one that matters. If you just spin both knobs randomly instead, you end up trying way more distinct settings of the knob that actually matters, for the same number of tries. That's the whole surprising result below: most models have a few "real" knobs and several "broken" ones, and grid search doesn't know which is which — random search doesn't need to.

</ELI5>

## Grid Search vs. Random Search — the Real Result, Not the Obvious One

The obvious intuition is that a denser, more systematic grid search should beat randomly guessing. Bergstra and Bengio's ["Random Search for Hyper-Parameter Optimization"](https://jmlr.org/papers/v13/bergstra12a.html) (JMLR, 2012) shows this is backwards, and explains precisely why: across real deep belief network tuning tasks spanning 32 hyperparameter dimensions, pure random search matched or beat grid and manual search — and a Gaussian-process analysis of validation performance as a function of the hyperparameters revealed that **for most datasets, only a few of the hyperparameters actually matter**.

That single fact is what breaks grid search. A $k \times k$ grid over two hyperparameters spends $k^2$ evaluations — but if only one of those two hyperparameters is actually important, every one of those $k^2$ evaluations only ever tries $k$ *distinct* values of the dimension that matters, because each of the $k$ important-dimension values gets repeated $k$ times while the unimportant dimension varies. Random search, drawing $k^2$ independent samples, tries close to $k^2$ distinct values of *every* dimension — including the one that matters — for the identical evaluation budget.

### See the Distinct-Values Gap For Real

The diagram above illustrates the claim; here it is proven with a real count, for a real budget. Say only hyperparameter $A$ actually matters (call it "learning rate") and hyperparameter $B$ doesn't ("some knob that turns out not to matter") — a $k\times k$ grid spends $k^2$ evaluations but every one of them only ever tries $k$ *distinct* values of $A$, since each of those $k$ values gets repeated $k$ times as $B$ varies underneath it. Count it yourself, for the exact same evaluation budget:

<RunnableCode code={`import numpy as np

def grid_search_distinct_values(k):
    """k x k grid over (A, B). Returns (distinct A values tried, total evaluations)."""
    grid_A = np.linspace(0, 1, k)
    grid_B = np.linspace(0, 1, k)
    evaluated_A = [a for a in grid_A for b in grid_B]  # k^2 evaluations total
    return len(set(evaluated_A)), len(evaluated_A)

def random_search_distinct_values(n_evals, seed=0):
    """n_evals random (A, B) draws. Returns (distinct A values tried, total evaluations)."""
    rng = np.random.default_rng(seed)
    A = rng.uniform(0, 1, n_evals)
    return len(set(A.tolist())), n_evals

k = 20
budget = k * k  # same total evaluation budget for both methods: 400

grid_distinct, grid_total = grid_search_distinct_values(k)
random_distinct, random_total = random_search_distinct_values(budget)

print(f"Same budget: {budget} evaluations each.")
print(f"Grid search:   {grid_distinct} distinct values of the ONE dimension that matters",
      f"(out of {grid_total} evaluations -- {grid_total - grid_distinct} were redundant re-tests of an already-tried value).")
print(f"Random search: {random_distinct} distinct values of that same dimension",
      f"-- {random_distinct / grid_distinct:.0f}x more, for the identical budget.")

# Try raising k (say, to 40 -- an 1600-evaluation budget) and re-run:
# grid search's distinct-value count only ever grows as k, random search's
# grows as k^2 -- the gap widens, it doesn't stay fixed.

<GoDeeper title="Go deeper: how many random draws until you're confident you've hit the good region?">

This has a clean, real answer, independent of anything about the model being tuned. Say the top $X$ fraction of the hyperparameter space counts as "good" (e.g. the top 5%, so $X = 0.05$) — with $N$ independent random draws, the probability that *none* of them land in that good region is $(1-X)^N$, since each draw independently misses it with probability $1-X$. So the probability at least one draw *does* land in the good region is $1 - (1-X)^N$. Plugging in $X = 0.05$: at $N=20$ draws, that's $1 - 0.95^{20} \approx 64\%$; by $N=60$, it's $1 - 0.95^{60} \approx 95\%$. This is exactly why random search needs surprisingly few evaluations to be confident of finding a near-optimal setting — the sample size needed depends only on how large you consider the "good" region to be, not on the number of hyperparameters or how the model itself behaves, which is part of why the guarantee holds even for models nobody understands well enough to reason about directly.

</GoDeeper>

## Bayesian Optimization: Using Every Result to Pick the Next One

Grid and random search are both **open-loop**: every point to evaluate is decided in advance, before seeing a single result. Bayesian optimization is **closed-loop** — it builds a probabilistic model of "hyperparameters → validation score" from every evaluation run so far, and uses that model to choose the next point deliberately.

The standard surrogate model is a **Gaussian Process (GP)**: at any untried hyperparameter setting $x$, the GP gives both a predicted score $\mu(x)$ and an uncertainty $\sigma(x)$ — confident and low-uncertainty near points already evaluated, uncertain and high-variance far from anything tried yet. The next point to evaluate is chosen by maximizing an **acquisition function** built from $\mu$ and $\sigma$; the standard choice, **Expected Improvement (EI)**, is (see [Distill's "Exploring Bayesian Optimization"](https://distill.pub/2020/bayesian-optimization/)):

$$EI(x) = \big(\mu(x) - f(x^+) - \epsilon\big)\,\Phi(Z) + \sigma(x)\,\phi(Z), \qquad Z = \frac{\mu(x) - f(x^+) - \epsilon}{\sigma(x)}$$

where $f(x^+)$ is the best score found so far, $\Phi$/$\phi$ are the standard normal CDF/PDF, and $\epsilon$ is a small constant controlling how much improvement counts as worth chasing. The formula is worth reading as two additive terms, not one opaque expression: $(\mu(x)-f(x^+)-\epsilon)\Phi(Z)$ rewards points predicted to beat the current best — **exploitation** — and $\sigma(x)\phi(Z)$ rewards points the model is simply uncertain about, regardless of predicted value — **exploration**. EI is high when either term is high, which is exactly the mechanism that keeps Bayesian optimization from just greedily re-exploring the best region found so far.

This sequential, informed selection is why Bayesian optimization typically needs far fewer evaluations than grid or random search to reach a comparable result — a real, practically significant gap when each evaluation is an expensive full training run — at the real cost of being inherently sequential (each point depends on all previous results) rather than trivially parallelizable the way grid/random search are.

## Successive Halving and Hyperband

A different lever entirely: instead of choosing *which* configurations to try more cleverly, spend the *budget* per configuration adaptively. **Successive halving** allocates a small budget (a few epochs, a data subsample) to many configurations at once, discards the worst-performing half, and gives the survivors a larger budget — repeating until one configuration remains. This exploits a real empirical regularity: a bad hyperparameter configuration is usually identifiable early, well before training to completion, so the real budget only ever goes toward configurations that already looked competitive. **Hyperband** wraps successive halving in an outer loop that varies the initial budget-vs-configuration-count tradeoff itself, hedging against picking a bad tradeoff for problems where it isn't obvious in advance whether wide-and-shallow or narrow-and-deep search will win.

## Choosing an Approach

- **Few hyperparameters, cheap evaluations**: random search is a strong, simple default — Bergstra & Bengio's result holds precisely here.
- **Expensive evaluations (full training runs), evaluation budget matters most**: Bayesian optimization's sample efficiency is worth its sequential-only constraint.
- **Cheap early signal available (can tell early if a run is bad)**: successive halving / Hyperband, often combined *with* Bayesian optimization for choosing which configurations to allocate budget to in the first place (the approach real tools like Optuna and Ray Tune default to).
- **Grid search**: rarely the right default given the result above — reach for it only when a hyperparameter genuinely has just 2-3 sensible discrete choices worth enumerating exhaustively, not as the general-purpose method.
